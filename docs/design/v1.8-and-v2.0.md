# v1.8 + r1.9 + v2.0 — Scheduler, self-hosting, console, and stable extensions

Status: implementation plan. Baseline: `main` at `ac0b032` (`v1.7.2`) on
2026-08-09. This document is the delivery and PR-review contract for finishing
the public roadmap. It does not authorize direct work on `main` or release tags;
each slice lands through a feature branch, PR, and required CI.

## Goal

Finish the remaining roadmap in dependency order:

1. v1.8 adds durable local cron/interval schedules, a scheduler tick loop,
   schedule CLI/API operations, and a localhost-first backend runtime image.
   Its self-host scope is backend-only.
2. r1.9a containerizes and publishes the separately owned operator console,
   then composes that immutable image with the backend runtime.
3. v2.0 establishes one documented, typed `agent_os.api` import surface for
   memory connectors, backend adapters, policy engines, and native skill
   packages, with a checked-in signature contract that CI will reject if it
   drifts.

Every numbered slice below is independently shippable: it has a useful outcome,
an explicit file/function boundary, exclusions, and a verification command. A
later slice may depend on an earlier one, but no slice should contain dormant
code that only becomes testable several PRs later.

## Non-negotiable decisions

### Scheduler persistence is physically separate

The scheduler uses its **own SQLite file**. With the default checkpoint path,
the files are:

```text
checkpoints.db          # async LangGraph checkpointer
checkpoints.runs.db     # synchronous v1.7 run ledger
checkpoints.sched.db    # synchronous v1.8 scheduler store
```

`AGENT_OS_SCHED_DB` overrides the scheduler path. Otherwise the scheduler path
is derived exactly as `agent_os/runs.py::_get_db_path()` derives the run-ledger
path: split the configured `AGENT_OS_CHECKPOINTS_DB` path and insert `.sched`
before its extension (`state.sqlite` becomes `state.sched.sqlite`; an
extensionless path gets `.sched.db`). Every scheduler connection sets WAL and
`busy_timeout=30000`.

The scheduler must never create tables in, attach, or synchronously write to the
async checkpointer file. WAL and `busy_timeout` do not make sharing safe. The
v1.7 real E2E established that a synchronous writer can block the event loop
which must release the async checkpointer lock, producing a hard deadlock. See
[`v1.7-run-ledger-runtime-api.md`](v1.7-run-ledger-runtime-api.md).

### Schedule and execution semantics

- A schedule has `kind=run|brief|app_callback` and exactly one trigger: a five-field POSIX
  cron expression or a positive interval.
- All persisted timestamps are aware UTC ISO-8601 strings. Cron schedules also
  store an IANA timezone (default `UTC`) so daylight-saving behavior is
  reproducible; interval schedules are elapsed-time schedules and reject a
  non-UTC timezone.
- A due occurrence is claimed and its next occurrence is advanced in one
  `BEGIN IMMEDIATE` transaction. This prevents two local `serve` processes from
  dispatching the same occurrence.
- Missed occurrences coalesce: one due dispatch is created, then `next_run_at`
  advances to the first future occurrence. v1.8 does not create a catch-up
  storm.
- `run-once` dispatches immediately without changing `next_run_at` and works
  even when a schedule is disabled. Removing a schedule does not cancel work
  that it already dispatched.
- Every scheduled `run` creates a fresh `thread_id` and run-ledger row, then
  calls `agent_os.server.run_executor.execute_run()`. It must not duplicate the
  graph-driving code. A run that reaches human approval remains `interrupted`
  in the run ledger and is resumed through the existing runtime API.
- A scheduled `brief` uses the same brief service as CLI/API brief generation,
  calculates the date when it fires, and writes through the existing gated
  memory write path.
- The tick loop is part of `agent-os serve`. The base CLI can add, list, remove,
  and manually dispatch schedules without installing the `[serve]` extra, but
  automatic firing requires a long-running server (or the self-host stack).
- The scheduler is enabled by default in `serve` and can be disabled with
  `AGENT_OS_SCHEDULER_ENABLED=false`, primarily for embedding and tests. Tick
  cadence is configurable with `AGENT_OS_SCHED_TICK_SECONDS` and defaults to 1
  second.

### Self-hosting boundary

The v1.8 self-host scope is **backend-only**: r1.8b.1 provides the runtime
container and was smoke-verified in PR
[#41](https://github.com/simon-aibc/agent-os-langgraph/pull/41). The former
r1.8b.2 console-in-Compose slice is deferred and must not block v1.8.0.

The operator console remains a separately owned public repository/artifact, as
decided in the v1.7 design. This repository must not copy `dashboard/`, vendor
the frontend, or use a placeholder/floating console image merely to claim a
combined self-host stack.

The combined stack moves to r1.9a. That slice starts in the separate
`agent-os-console` repository by adding a Dockerfile and publishing a versioned
GHCR image. Only after its immutable digest, container port, API-base
environment contract, and v1.8 schedule support are available may this
repository add Compose wiring pinned to that digest.

The v1.8 backend is reached through `127.0.0.1:4680`. The r1.9a stack
additionally publishes the console on `127.0.0.1:4100`. Binding publicly,
TLS, authentication, multi-user tenancy, and managed-cloud deployment remain
outside this roadmap.

### v2 compatibility boundary

Only names exported from `agent_os.api` are covered by the v2 extension
compatibility promise. Existing implementation modules such as
`agent_os.connectors`, `agent_os.backends`, `agent_os.policy`, and
`agent_os.skill_packages` remain importable but are not independently frozen.
The facade initially re-exports the actual runtime objects—there must not be a
second set of look-alike Protocols whose runtime identities can diverge.

Compatible minor releases may add optional methods, new exports, or parameters
with defaults. Removing/renaming an export, changing parameter order or kind,
removing a default, narrowing accepted inputs, or changing a return contract
requires a deprecation cycle and the next major release.

| Risk | Prevention in this plan | Release evidence |
|---|---|---|
| SQLite deadlock with LangGraph | Dedicated `.sched` file; isolation regression test | Three distinct DB paths during real E2E |
| Duplicate local dispatch | Transactional due claim and next-time advance | Concurrent-tick test plus restart smoke |
| Event-loop starvation | Brief work goes through `asyncio.to_thread`; bounded child tasks | Responsiveness and clean-shutdown tests |
| Schedule drift/catch-up storm | UTC persistence, explicit cron timezone, missed-fire coalescing | Injected-clock recurrence tests |
| Backend self-host image does not actually boot | Wheel-only non-root image and real CLI serve smoke | Healthy container and `/api/health` response |
| Console release exists only in a local cache | Require an anonymous exact-digest registry lookup and clean pull | GHCR manifest response plus clean-clone Compose smoke |
| Secrets or private state enter images | Narrow build context, runtime env injection, persistent volumes | Build-context/static secret review |
| v2 freezes accidental internals | Small explicit facade and documented compatibility boundary | Golden signature plus behavior tests |

## Slice r1.8a.1 — Schedule store and recurrence engine

### Target and acceptance

Create a synchronous scheduler repository that mirrors the proven separate-file
pattern in `agent_os/runs.py`. It validates schedules before persistence,
calculates deterministic next-fire timestamps, exposes atomic due claims, and
does not import FastAPI or graph code.

Persist this schema (small naming adjustments are acceptable only if all
semantics and tests remain unchanged):

```sql
CREATE TABLE IF NOT EXISTS schedules (
    schedule_id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    kind TEXT NOT NULL CHECK (kind IN ('run', 'brief', 'app_callback')),
    trigger_kind TEXT NOT NULL CHECK (trigger_kind IN ('cron', 'interval')),
    trigger_value TEXT NOT NULL,
    timezone TEXT NOT NULL,
    payload TEXT NOT NULL,
    enabled INTEGER NOT NULL DEFAULT 1,
    next_run_at TEXT NOT NULL,
    last_run_at TEXT,
    last_status TEXT,
    last_error TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS schedules_due_idx
    ON schedules(enabled, next_run_at);
```

`payload` is JSON. For `run` it contains `task` and optional `workspace`; for
`brief` it is empty in v1.8 and uses the server's configured connector/profile.
Unknown payload keys are rejected at the CLI/API boundary rather than silently
stored.

### Files and functions

- **New `agent_os/schedules.py`**
  - constants `SCHED_DB_ENV = "AGENT_OS_SCHED_DB"` and the allowed kinds and
    trigger kinds;
  - `_get_db_path()`, `_connect()`, `_init_schedules_db()` mirroring
    `agent_os/runs.py`, including WAL and 30-second busy timeout;
  - `create_schedule(...) -> str`, `get_schedule(schedule_id)`,
    `list_schedules(*, kind=None, enabled=None)`, and
    `remove_schedule(schedule_id) -> bool`;
  - `set_schedule_enabled(schedule_id, enabled)` as a storage primitive even
    though enable/disable CLI commands are deferred;
  - `claim_due_schedules(now, *, limit) -> list[dict]`, atomically selecting due
    rows and advancing each `next_run_at` before commit;
  - `record_schedule_result(schedule_id, *, status, error=None)`;
  - JSON decode rows on read and never return raw payload strings.
- **New `agent_os/schedule_recurrence.py`**
  - `parse_interval(value: str) -> datetime.timedelta`, accepting integer
    seconds plus human forms `30s`, `5m`, `2h`, and `1d`;
  - `validate_cron(expression, timezone)` and
    `next_run_at(trigger_kind, trigger_value, timezone, *, after)`;
  - coalescing helper that advances from the persisted occurrence until the
    result is later than `now`.
- **Modify `pyproject.toml`** to add one pinned cron parser dependency to core
  dependencies. Pin the reviewed current version; do not hand-roll a partial
  cron parser.
- **New `tests/test_schedules.py`** for schema, CRUD, filtering, validation,
  payload round-trip, interval/cron/timezone boundaries, coalescing, and atomic
  claim behavior.
- **New `tests/test_schedule_db_isolation.py`** asserting the derived path,
  `AGENT_OS_SCHED_DB` override, WAL and busy timeout, absence of scheduler
  tables in the checkpoint DB, and separate-file behavior while an async
  checkpointer connection is open.

### Out of scope

- Dispatching runs or briefs, a background loop, CLI/API routes, and UI.
- Calendar/holiday rules, seconds-level cron fields, natural-language times,
  dependencies between schedules, and distributed scheduling.
- A migration framework. Schema creation is idempotent; incompatible changes
  after v1.8 require an explicit future migration slice.

### Verification

```bash
python -m pytest -W error tests/test_schedules.py tests/test_schedule_db_isolation.py
python -m ruff check agent_os/schedules.py agent_os/schedule_recurrence.py tests/test_schedules.py tests/test_schedule_db_isolation.py
```

## Slice r1.8a.3 — Dispatcher, tick, and scheduler service

### Target and acceptance

Turn claimed schedule rows into real work. A `run` uses the v1.7 run ledger and
`execute_run`; a `brief` uses r1.8a.2. The tick is clock-injectable, bounded,
and safe when called concurrently. A service object owns the loop and all child
tasks so shutdown does not leak tasks.

### Files and functions

- **New `agent_os/scheduler.py`**
  - `ScheduleDispatchResult(schedule_id, kind, status, run_id=None, ref=None,
    error=None)`;
  - `async dispatch_schedule(schedule, *, manual=False)`; for `run`, generate a
    fresh thread UUID, call `runs.create_run(...)`, then `await execute_run(...)`
    and reflect the ledger's resulting status; for `brief`, call
    `execute_brief(write=True)` through `asyncio.to_thread()`;
  - `async run_scheduler_tick(*, now=None, capacity=...)` claims at most the
    available capacity and dispatches each claim exactly once;
  - `SchedulerService.start()`, `tick()`, and `stop()`; maintain strong
    references to child tasks, reap completed tasks, log failures without
    killing the loop, and stop accepting work during shutdown;
  - interpret `AGENT_OS_SCHED_TICK_SECONDS` with a positive lower bound and use
    monotonic sleeping while UTC wall time determines due work.
- **New `tests/test_scheduler.py`** covering run delegation (including the exact
  `execute_run` call), brief delegation, fresh run/thread IDs, interrupted and
  failed outcomes, concurrent ticks, capacity, failure isolation, and clean
  shutdown.

### Out of scope

- Retrying a run or brief after it starts, resuming orphaned in-flight work
  after process death, hard-cancelling graph execution, priority queues, and
  multi-host leader election. Atomic claiming prevents duplicate claims; v1.8
  does not promise exactly-once completion across a process crash.
- Sending notifications for failures or approvals.

### Verification

```bash
python -m pytest -W error tests/test_schedules.py tests/test_scheduler.py tests/test_runs.py tests/test_run_executor.py
python -m ruff check agent_os/schedules.py agent_os/schedule_recurrence.py agent_os/scheduler.py tests/test_schedules.py tests/test_scheduler.py
```

## Slice r1.8a.4 — Schedule CLI

### Target and acceptance

Ship the required local operator contract:

```text
agent-os schedule add --name NAME --kind run --cron "0 9 * * *" --task TASK [--timezone AREA] [--workspace PATH]
agent-os schedule add --name NAME --kind brief --every 24h
agent-os schedule add --name NAME --kind app_callback --every 1h --url URL [--method METHOD] [--headers JSON] [--body JSON]
agent-os schedule list [--kind run|brief|app_callback] [--enabled true|false] [--json]
agent-os schedule remove SCHEDULE_ID
agent-os schedule run-once SCHEDULE_ID
```

`add` requires exactly one of `--cron` and `--every`; requires `--task` for a
run; and rejects `--task`/`--workspace` for a brief. Human list output includes
ID, name, kind, trigger, timezone, enabled, next run, last status, and last
error. JSON output contains the repository rows without lossy reformatting.
`remove` and `run-once` return exit code 2 for an unknown ID. A dispatched run
prints its `run_id` and resulting status; a brief prints its written ref.

### Files and functions

- **Modify `agent_os/cli/app.py`**
  - add `schedule` and its four nested subparsers in `build_parser()`;
  - include `schedule` in `_normalize_argv()`;
  - add `_handle_schedule_command(args, formatter) -> Awaitable[int]` before
    graph/profile initialization so CRUD remains offline and lightweight;
  - delegate persistence and dispatch to `agent_os.schedules` and
    `agent_os.scheduler`; do not copy their logic into argparse handlers.
- **Modify `agent_os/cli/formatter.py`** only for reusable schedule table/result
  rendering; JSON remains plain stdout for scripting.
- **New `tests/test_schedule_cli.py`** covering parser help, all valid forms,
  mutual exclusion and kind-specific validation, human/JSON list output,
  unknown IDs, exit codes, and run-once delegation.
- **Modify `tests/test_cli.py`** to assert the installed command exposes
  `schedule --help` without regressing legacy naked-task normalization.

### Out of scope

- `edit`, `enable`, `disable`, daemon, watch, or history commands; interactive
  prompts; accepting schedule names in place of IDs.
- Calling the Runtime API from the CLI. The CLI operates on the local scheduler
  DB by design.

### Verification

## Slice r1.8a.5 — Schedule Runtime API and `serve` lifecycle

### Target and acceptance

Add the required API without changing existing run endpoints:

- `GET /api/schedules?kind=&enabled=` returns schedule rows ordered by
  `created_at DESC`.
- `POST /api/schedules` validates and creates a schedule, returning HTTP 201
  with the full persisted row (including computed `next_run_at`). The body uses
  `cron` or `every`, never both, and the same kind-specific payload rules as the
  CLI.

Use one shared request-to-domain validator so CLI and HTTP cannot drift on
accepted schedule shapes. FastAPI lifespan starts one `SchedulerService` after
app startup and stops it on shutdown. `AGENT_OS_SCHEDULER_ENABLED=false` skips
the service but leaves CRUD routes available. Importing the app must not start
a loop.

### Files and functions

- **New `agent_os/schedule_models.py`** with a FastAPI-independent Pydantic domain
  input model used by CLI and API, including the cron/every and kind/payload
  cross-field validation.
- **Modify `agent_os/server/api.py`**
  - add `CreateScheduleRequest`, `list_schedules_endpoint()`, and
    `create_schedule_endpoint()`;
  - add an async lifespan context that owns exactly one `SchedulerService`;
  - retain localhost CORS defaults and every v1.7 route/response.
- **Modify `agent_os/cli/app.py`** to construct the same domain input model from
  parsed arguments before calling `create_schedule()`.
- **New `tests/test_schedule_api.py`** covering GET/POST, 201/422 responses,
  filter behavior, exact response shape, DB isolation, and disabled-scheduler
  mode.
- **New `tests/test_server_lifespan.py`** proving start/stop, one loop per app
  lifespan, no loop at import, and no task leaks.
- **Modify `tests/test_api.py`** only to preserve all existing v1.7 API
  regression coverage.

### Out of scope

- API delete, run-once, edit, enable/disable, or schedule-event streaming.
- Remote authentication, authorization, rate limiting, and CORS expansion.
- Running the tick loop in every CLI invocation or as a second OS daemon.

### Verification

was not part of the v1.8 release gate because the console is separately owned.


`agent_os.api.__all__` is explicit. All types referenced by a frozen signature
are either built-ins/standard typing objects or exported from this facade. The
facade re-exports object identity (`agent_os.api.MemoryConnector is
agent_os.connectors.MemoryConnector`), not wrappers.

The native skill package filesystem contract frozen for v2 is:

- one directory containing `manifest.toml`;
- required `[skill]` keys `name` and `version`;
- one or more `[[skill.handlers]]` entries with a non-empty `match` list and an
  `entrypoint = "module:function"` relative to that package directory;
- canonical command is the first `match` item and the remainder are aliases;
- handler is a LangChain `BaseTool` or callable invoked with keyword arguments;
- duplicate names/aliases fail through `SkillRegistry` and malformed manifests
  raise `ValueError` with the manifest path.

Tighten the current loader to this contract before calling it stable; do not
freeze its current silent return for missing required manifest fields.

## Antigravity PR review protocol

Review Antigravity's PRs against this document in the dependency order above.
For each arriving PR:

1. Record the claimed slice and base commit. Reject a PR that silently combines
   later slices or release/tag operations unless the dependency table is
   explicitly amended first.
2. Compare the changed-file list to the slice's files/functions and out-of-scope
   section. Unrelated cleanup is split out.
3. Inspect tests before implementation details: every acceptance statement,
   failure path, and storage/security invariant needs a regression assertion.
4. Independently run the slice verification and full gates; executor or PR-body
   claims are not evidence.
5. For scheduler changes, inspect `_get_db_path()` and every `sqlite3.connect`
   call first. Any scheduler access to the checkpoint file is a release blocker.
6. For run dispatch, require a direct call to the existing `execute_run()` and
   a fresh run-ledger row. Any copied graph stream loop is a release blocker.
7. For r1.8 backend self-hosting, inspect the pinned base image, build-context
   exclusions, non-root paths, and real container health smoke. For r1.9a,
   additionally render `docker compose config`, inspect resolved host bindings
   and the published console digest, then perform the persistence restart smoke.
8. For v2, review any golden-contract diff line by line and verify all public
   examples import contracts from `agent_os.api`.
9. Report findings by severity with exact file/line references, then state the
   merge verdict and missing evidence. “No findings” still lists commands run
   and any residual risk.

Immediate rejection conditions are: direct changes or tags on `main`; a shared
scheduler/checkpointer SQLite file; absent WAL/busy timeout; no atomic due claim;
scheduled runs bypassing `execute_run`; a floating/unpublished console image;
non-loopback default port publication; committed secrets; or a public signature
change with no reviewed contract/docs update.
