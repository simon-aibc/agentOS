# v1.7 — Run Ledger + EventStore + Runtime API

Status: design (approved scope 2026-08-08). Backbone-first: ship r1.7a–c and tag `v1.7.0`. The Web Operator Console (block D) is a separate later effort — the existing `dashboard/` will be **migrated out** into its own repo and re-pivoted to the operator IA against this API.

## Goal

Expose structured runtime interfaces so an external orchestrator or an operator console can start runs, observe them event-by-event, and approve/cancel interrupted runs — persisted durably in the existing `checkpoints.db`.

## Design decisions

- **Storage**: a dedicated ledger SQLite file, **derived** from the checkpoint path (`./checkpoints.db` → `./checkpoints.runs.db`; override with `AGENT_OS_RUNS_DB`). Two tables: `runs`, `run_events`. Mirrors the `sessions` table pattern in `agent_os/sessions.py`.
  - **Why not the same file (revised after real E2E)**: the original plan put these tables in `checkpoints.db`. Real end-to-end testing proved a hard deadlock — the *synchronous* ledger writer and the *async* LangGraph checkpointer writing the same file on the same event loop deadlock: the blocking ledger call freezes the loop that would let the checkpointer release its write lock, surfacing as instant `database is locked` even under WAL + `busy_timeout=30000`. A separate file gives each writer its own lock; the two concerns never needed a cross-transaction. WAL + busy_timeout are retained on the ledger as hygiene.
- **Run vs session vs thread**: a *run* is one graph invocation on a `thread_id`. A run row references its `thread_id` (the LangGraph checkpoint key). Sessions remain the conversational index; runs are the execution ledger. Multiple runs can share a thread (resume/approve continues the same thread).
- **Approve/cancel semantics**: LangGraph interrupts surface via `task.interrupts` (see `_pending_interrupt` in `agent_os/cli/app.py`). **Approve** = `graph.astream_events(Command(resume=<feedback>), config)`. **Cancel** = mark run `cancelled` and do not resume; the checkpoint is left intact (no hard kill of an in-flight process in v1.7 — cancel applies to interrupted/pending runs).
- **Events**: every meaningful graph event is appended to `run_events` with a monotonic per-run `seq`. SSE replays from a client-supplied `?after=<seq>` offset so a reconnecting console never loses events.

## Data model

```sql
CREATE TABLE IF NOT EXISTS runs (
    run_id TEXT PRIMARY KEY,          -- uuid4
    thread_id TEXT NOT NULL,          -- LangGraph checkpoint key
    workspace TEXT,                   -- workspace name or NULL
    status TEXT NOT NULL,             -- queued|running|interrupted|completed|cancelled|error
    task TEXT,                        -- initial task/prompt (truncated)
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    ended_at TEXT,
    error TEXT                        -- error message if status=error
);

CREATE TABLE IF NOT EXISTS run_events (
    run_id TEXT NOT NULL,
    seq INTEGER NOT NULL,             -- monotonic per run, starts at 1
    ts TEXT NOT NULL,
    kind TEXT NOT NULL,               -- status|node|token|interrupt|result|error
    payload TEXT NOT NULL,            -- JSON
    PRIMARY KEY (run_id, seq)
);
```
